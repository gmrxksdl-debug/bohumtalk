# 보험톡 카드뉴스 자동화 PRD 및 대화 기반 개발 회고

- 작성일: 2026-11-02, Asia/Seoul
- 독자: AI 전문 강사, 후속 개발자, 제품 기획자
- 범위: 이 대화에서 진행한 보험톡 일일 카드뉴스 자동화와 조직원용 Team Studio 초기 버전
- 목적: 사용자가 무엇을 원했고, 어떤 실패와 수정 요청을 거쳐 현재 구조가 되었는지 이해하고 후속 개발을 판단하도록 한다.
- 근거 수준: 대화 기록, 로컬 코드/README/테스트 파일, 날짜별 산출물 목록. 이번 문서 작성 중 모든 과거 테스트나 외부 API를 재실행한 것은 아니다.
- 이 문서는 축어록이 아니다. 요구와 결정은 요약하며, 인증정보와 개인 컴퓨터 경로는 공유하지 않는다.
- 기존 저장소의 루트 PRD에는 다른 대화에서 확장된 프로젝트 이력이 있다. 이 문서는 그 내용을 삭제하거나 모두 검증했다고 주장하지 않는 별도 보충 문서다.

## 1. 강사님께 먼저 전달할 요약

사용자는 보험 분야 인스타그램 계정을 운영하면서, 자신이 팔로우하는 계정의 피드·릴스를 참고해 매일 카드뉴스를 만들고 싶어 했다.
최종 합의는 '후보 여러 개 → 오늘 주제 하나 → 하나의 이야기로 연결된 7장 → 캡션·프롬프트·PNG·검수·ZIP 저장'이다.

가장 중요한 전환은 디자인을 더 자세히 프롬프트에 적는 것만으로는 로고·계정명·카테고리·페이지번호의 위치가 고정되지 않았다는 점이다.
그래서 AI에는 본문만 생성시키고, 고정 요소는 원본 로고와 폰트를 이용한 동일 코드 레이어로 합성하도록 바꾸었다.

이후 사용자는 개인 자동화를 조직원에게 배포할 프로그램으로 확장하고자 했다.
각 조직원이 자기 로고·인스타그램 아이디·디자인 참고 이미지를 등록하는 로컬 웹앱 초기 버전이 존재하지만, 다중 사용자 운영 서비스 출시나 유료 AI API 실호출 검증이 완료된 것은 아니다.

### 현재 상태를 한 줄로

**카드뉴스 생성과 고정 합성의 작업 흐름은 존재한다. 안정적인 인스타그램 수집·본문 품질 자동 승인·외부 팀 서비스 운영은 아직 완성되지 않았다.**

## 2. 원래 문제와 사용자

### 2.1 업무 문제

- 소재 탐색, 원고 구성, 이미지 제작, 브랜드 삽입, 페이지 정렬, 캡션 작성이 반복된다.
- 생성 이미지마다 브랜드 요소 크기와 위치가 달라 하나의 계정 콘텐츠처럼 보이지 않는다.
- AI가 독자의 실제 보험 상담 순서를 이해하지 못하면 내용이 자연스러워도 실무적으로 틀릴 수 있다.
- 대화에만 결과를 남기면 자료를 찾거나 조직원에게 인계하기 어렵다.
- 조직원별 브랜드를 지원하려면 특정 계정에 하드코딩한 자동화에서 제품으로 전환해야 한다.

### 2.2 대상

| 대상 | 필요 |
|---|---|
| 보험톡 운영자 | 매일 소재·7장·캡션·파일 묶음 확보, 빠른 검토 |
| 30~40대 직장인·가장·기혼 독자 | 불안 공감, 저장할 실무 체크, 과장 없는 상담 연결 |
| 조직 관리자 | 멤버 초대, 운영 설정, 사용량과 실패 확인 |
| 조직원 | 자기 로고·아이디·샘플로 개인 카드뉴스 제작 |
| 전문 강사·개발자 | 실패 원인·구현 범위·검증 수준을 구분한 인계 |

## 3. 대화에서 요구가 바뀐 과정

초기 메시지의 정확한 발화 날짜는 확인되지 않으므로 순서로 기록한다.
자동화 실행 날짜와 문서 작성 날짜는 사용자 요청 시각과 같은 의미가 아니다.

| 단계 | 사용자 요청·문제 제기 | 합의·대응 | 배운 점 |
|---|---|---|---|
| 1 | Codex 자동화 설명 후 원하는 작업과 시간을 질문해 달라 | 반복 업무의 입력·시간·출력 정의 시작 | 단순 예약 전에 결과물을 구체화해야 함 |
| 2 | 웨일에서 로그인된 인스타그램의 팔로우 피드·릴스를 읽고 보험 소재 제작 | 웨일 세션 접근과 읽힌 신호 기록을 시도 | 로그인된 브라우저와 도구가 연결된 브라우저는 다름 |
| 3 | 매일 오전10시, 실제 PNG 생성, 보험 분야, 기존 카드 톤 유지 | 한국시간 일일 실행과 이미지 산출물 요구 | 대본만으로 완료 처리하면 안 됨 |
| 4 | 내일 작업을 지금 실행, 웨일 자동화 모드 허용 | 수동 실행과 접근 방식 점검 | 보안 화면 우회나 세션 추출은 허용하지 않음 |
| 5 | 디자인 불만, 릴스·카드를 읽고 장별 프롬프트를 만든 뒤 Canva 활용 제안 | 장별 기획과 디자인 기준 구체화 | 도구 이름만 바꿔도 품질이 해결되지는 않음 |
| 6 | 페이지마다 주제가 다른 결과에 강한 불만 | 후보는 여러 개지만 최종 주제는 하나로 고정 | '6장'과 '소재6개' 혼동을 제거 |
| 7 | 인계 문서를 빠짐없이 반영하고 자동화에 기준을 내장 | v4.8 규칙을 자동화 본문에 포함 | 매번 큰 외부 문서를 다시 읽는 비용 감소 |
| 8 | 장수를7장으로 줄이고 부딪힐 요소를 수정 | 7장 구조·모듈·실패시 대체 경로 확정 | 길이와 상태를 구조화 |
| 9 | 앞으로 묻지 말고 진행 | 승인된 범위에서는 자율 진행 | 비밀번호·유료 과금·권한 경계를 넘어서는 허가는 아님 |
| 10 | 매일 이 대화 전달과 컴퓨터 파일 저장까지 요청 | 날짜 폴더·PNG·대본·QA·manifest·ZIP 규칙 | 파일 존재 확인까지 완료 정의에 포함 |
| 11 | 원본 보험톡 로고를 작은 크기로 고정, 좌상단 선택 | 모든7장 좌상단 원본 로고 합성 | 이전 '좌상단 금지' 규칙을 최신 요청으로 대체 |
| 12 | 번호 크기, 회색 카테고리 박스, 아이디, 로고가 흔들린다 | 고정 요소를 생성 모델에서 분리해 동일 렌더러 사용 | 확률적 생성과 결정적 조판의 역할 분리 |
| 13 | 알릴의무 주제에서 청약서 질문 순서가 실무와 맞지 않음 | 설계 의뢰 전 병력 정리→상담→상품별 질문→청약 재확인 | 도메인 전문가인 사용자의 피드백이 핵심 |
| 14 | 조직원에게 배포할 프로그램으로 만들고 싶다 | 개인 브랜드·샘플 업로드·대본 편집·고정 합성·ZIP 앱 구성 | 1인 스크립트에서 사용자별 데이터 격리가 필요한 제품으로 변화 |
| 15 | 로컬 사이트 연결 안 됨 | 자체 응답 확인 후 브라우저를 여는 실행기 추가 | localhost 링크 제시와 실제 접속 성공은 구분 |
| 16 | 강사에게 대화와 발전 과정을 PRD로 공유, 생성자료도 GitHub 업로드 | 이 문서와 별도 산출물 색인 작성 | 내부 자료 전체 업로드가 아니라 공유 범위를 선별 |

## 4. 현재 일일 제작 흐름

1. 한국시간 실제 실행일을 계산하고 당일 산출물 존재 여부를 확인한다.
2. 웨일 자동화 포트9222에서 Instagram 타깃을 찾고, 접근 가능할 때만 현재 피드 텍스트·게시물 링크를 읽는다.
3. 로그인·보안 확인·CAPTCHA·2FA가 나오면 중단하고 우회하지 않는다.
4. 접근이 안 되면 '인스타 접근 불가'를 기록하고 보험 상시 소재로 진행한다.
5. 읽은 게시물이3개 미만이면 읽힌 신호와 상시 소재를 구분해 섞는다.
6. 후보3~5개를 제시한 뒤 저장 가치가 높은 주제 하나를 고른다.
7. 사실 검토 후 하나의 이야기로 연결된7장 원고·모듈·프롬프트·캡션을 만든다.
8. 장당 한 번씩 실제 이미지 생성을 시도한다. 실패한 장은 실패 상태를 기록한다.
9. 본문만 비율 유지 리사이즈하고 동일한 고정 레이어를 합성한다.
10. 고정 요소 픽셀·페이지 여백·규격을 검사하고, 본문은 오타·내용·디자인을 별도 검토한다.
11. 날짜 폴더, 문서, 상태 manifest, contact sheet, ZIP을 저장하고 검증한다.
12. 의미 있는 완료·실패만 대화에 알린다. 동일 결과의 중복 알림은 피한다.

위 절차는 목표/실행 규칙이다. 최근 인스타그램 읽기는 포트 접근 실패가 반복되어 실제 피드를 읽지 못한 날이 있었다.
그 날 생성한 소재를 '오늘 피드에서 발견한 유행'이라고 소개해서는 안 된다.

## 5. 7장 서사와 모듈

| 장 | 모듈 | 역할 |
|---|---|---|
| 1 | A | 문제를 자각시키는 질문형 훅 |
| 2 | B 또는 D | 검증된 데이터가 있으면 데이터, 없으면 개념·체감 |
| 3 | C 또는 D | 흐름·순서·구조·개념 |
| 4 | E | 오해와 진실 또는 선택지 비교 |
| 5 | B 또는 F | 비용·보장·서류·조건 또는 체크 |
| 6 | F 또는 A | 저장할 질문3개 또는 핵심 재강조 |
| 7 | G | 큰 댓글 키워드 CTA |

A=훅, B=데이터, C=타임라인, D=정의, E=비교, F=체크리스트, G=CTA.
수치가 없으면 억지 통계를 만들지 않는다. 댓글 CTA는 실제로 연결되지 않은 무료자료 자동발송·DM을 약속하지 않는다.

## 6. 디자인 규격과 흔들림 해결

### 6.1 고정 레이어

| 요소 | 규격 |
|---|---|
| 최종 이미지 | 1440×1920, 세로3:4 PNG |
| 로고 | 원본 파일, 좌95/상96/폭100px, 비율 유지 |
| 계정명 | 우95/상96px, @bohum__talk |
| 카테고리 | 좌95/상280px,260×56px,반경28px,7장 동일 문구 |
| 페이지번호 | 우95/하95px,01 / 07~07 / 07 |
| 일일 자동화 고정 글자 | Malgun Gothic Regular30px,#828282 |
| 카테고리 배경 | #F4F3F0 |
| 본문 배치 | 비율 유지, y400~1710 프레임 |
| 팀앱 폰트 | 배포용 Noto Sans KR Regular30px, 라이선스 파일 포함 |

개념상 상단14%·본문76%·하단10%로 분리한다.
카테고리 위치는 구체적인 픽셀 규칙을 우선하며, 본문 이미지는 고정 요소를 포함하지 않아야 한다.
계정명·페이지번호 정렬은 폰트 잉크 경계 기준으로 확인한다.
로고 자체의 파랑·검정·흰색은 원본을 유지하며 팔레트 예외다.

### 6.2 본문 스타일

흰 배경, 한국 에디토리얼, 타이포 중심의 플랫 그래픽.
본문은 넉넉한 면적을 사용하되 고정 레이어를 침범하지 않는다.
헤드라인/본문 크기 대비 약3:1, 강조는 크기 또는 색 중 하나.
어두운 배경·그라디언트·그림자·3D·포토리얼·글로우·외곽 가로 구분선은 금지한다.
1~7장 모두 같은 작은 좌상단 로고를 쓰며7장 중앙 큰 로고·중복 워터마크는 사용하지 않는다.

팔레트: #FFFFFF,#151515,#E74A1E,#0D5BF9,#EFA40C,#828282,#D8D7D7,#F4F3F0,#FEF0EB,#EBF1FD,#FDF6DF.

### 6.3 왜 프롬프트만으로 해결하지 않았나

생성 모델이 글자·로고·박스를 한꺼번에 그리면 같은 위치를 명령해도 픽셀 좌표·글자 폭·여백이 달라졌다.
따라서 본문은 AI가, 브랜드와 페이지 공통 요소는 코드가 담당한다.
코드/Pillow로 본문 디자인을 새로 그리는 것은 이 작업의 합의 범위 밖이다.
허용되는 코드는 고정 요소 합성·비율 유지 리사이즈·파일명·QA·축소 미리보기다.
고정 요소가 같다고 해서 본문의 오타·정보 정확성·3:1·팔레트까지 자동 통과한 것은 아니다.

## 7. 보험 내용과 안전 기준

- 수치·금액·통계·약관 조건을 발명하지 않는다.
- 필요한 최신 제도·약관은 공식 근거를 찾아 확인하고, 못 확인하면 [확인 필요]로 둔다.
- '무조건 지급', '확정 보상', 모든 보험사 공통이라는 단정을 피한다.
- 특정 상품의 예시 조건을 전체 보험에 일반화하지 않는다.
- 개인정보·증권·계좌번호를 공개 댓글로 요구하지 않는다.
- 게시 전 광고·모집 관련 검토 필요 여부를 운영자가 별도로 판단하도록 한다. 이 문서가 법률 검토를 대신하지 않는다.

수정: 설계 의뢰 전 병력·진단·소견 정리→설계사 상담 및 상품별 질문 확인→청약 단계 정식 답변 재확인.
최근3개월 진단·의심·추가검사, 상품별 기간 입원·수술, 최근5년 주요질환 등은 '예시'이며 모든 보험사의 동일 기준이 아니다.
설계사에게 말한 사실과 보험사에 대한 정식 고지 절차는 구분한다.
당시1장 지정 보조문구는 '기억에만 맡기기 전에 알릴의무사항부터 확인하세요.'였으며 다른 모든 주제에 반복하지 않는다.

## 8. 파일과 상태 관리

날짜별 폴더에는 카드7장, script-prompts-captions.md, QA.md, manifest.json을 저장한다.
고정 합성 시 fixed-layout.json,fixed-elements-overlay.png,fixed-elements-qa.json도 저장한다.
PNG가 있으면 contact-sheet.png와 날짜 ZIP을 만든다.
같은 날짜 수정은 v2,v3로 분리하며 원본을 덮어쓰지 않는다.
생성 도구 기본 폴더에만 남겨 두는 것은 지정 폴더 저장 완료가 아니다.
실제 파일 존재·7장 개수·PNG·1440×1920·빈 파일·ZIP 무결성을 확인한다.

## 9. 조직원 배포 제품 요구사항

### 9.1 핵심 사용자 흐름

## 10. 검증 근거와 한계

과거 작업 기록에서는6개 로컬 테스트와 실제 브라우저 UI 시험이 통과한 것으로 보고됐다.
이번 문서 작성에서는 테스트 함수·코드·README를 확인했으며, 그 테스트를 모두 새로 실행하지 않았다.
실제 유료 AI 호출은 미검증 상태다.

고정 요소 테스트는7장 헤더 y0~337 픽셀 비교와 우95/하95 페이지 잉크 경계를 확인한다.
최근 산출물은 고정 레이어 검증이 통과해도 미세 음영·질감·타이포 비율 문제 때문에 후보로 남아 있다.
따라서 'PNG7장이 있다'와 '게시 가능한 완성품7장'은 같은 상태가 아니다.

### 로컬 연결 문제

초기 localhost:8810 링크 접속이 안 된다는 사용자 피드백이 있었다.
도구 실행 환경의 프로세스/네트워크 범위와 사용자 브라우저의 접근 범위가 달라질 수 있었다.
응답을 확인한 후 실제 가용 포트를 브라우저에 여는 실행기를 추가했다.
실행기의 자기 HTTP 점검 성공은 다른 PC 접속이나 사용자의 실사용 성공까지 보장하지 않는다.
로컬 주소는 조직원에게 배포할 운영 주소가 아니다.
